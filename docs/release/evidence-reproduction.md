# Release Evidence Reproduction

NeonForge release evidence is generated on native macOS, Linux, and Windows hosts and
assembled into one content-addressed bundle. The bundle can be verified offline against
the same source checkout.

This procedure proves which workflow produced the recorded evidence. It does not claim
that NeonForge reproduced a benchmark publisher's machines, private judge, or external
leaderboard environment.

## Prerequisites

- Node.js 22 or newer, pnpm 12.4.2, and a `tar` command.
- Native access to macOS, Linux, and Windows. Cross-platform evidence cannot be inferred
  from a single-host run.
- Repository secrets `OPENAI_BASE_URL`, `OPENAI_API_KEY`, and `OPENAI_MODEL`. The model
  must resolve to the DeepSeek family.
- A Git checkout at the release commit. The evidence records both the Git commit and the
  `source-manifest.json` revision.

## Native CI Workflow

`.github/workflows/release-evidence.yml` runs on each native runner:

1. Install dependencies, scan the public tree for secrets/local paths, type-check, and run
   the unit/integration suite.
2. Build the platform installer and require its legal files.
3. Run the three protocol smokes and the 12-persona TUI/E2E suite.
4. Run the paired A/B benchmark on Linux only.
5. Upload the platform's `dist` output.

The aggregate Linux job downloads all platform artifacts, rejects stale or wrong-platform
inputs, assembles `dist/release-evidence`, verifies it offline, and creates
`dist/neonforge-release-evidence-<source-revision>.tgz`.

Configure the provider secrets in the repository settings, then either:

- Run the `release` workflow manually and set `publish_release=false` for a dry run.
- Push a `v*` tag. The `release` workflow runs the same evidence workflow, attests the
  bundle, and uploads the archive plus `SHA256SUMS` to the GitHub release.

The provenance attestation is generated by `actions/attest-build-provenance@v3` using
GitHub OIDC. Verify it with:

```bash
gh attestation verify neonforge-release-evidence-<revision>.tgz \
  --repo <owner>/<repository>
```

The workflow artifact is retained for 30 days. A GitHub release attachment is the
durable publication record.

## Local Reproduction

Each native host runs the same platform-specific commands:

```bash
pnpm install --frozen-lockfile
pnpm privacy:check
pnpm typecheck
pnpm test
pnpm build:custom
pnpm smoke:protocols
pnpm test:personas
```

Run `pnpm benchmark:ab` once on Linux. Collect each host's `dist` directory under a
common input root, preserving paths such as `smoke/linux-tui.json` and
`installers/neonforge-linux-x64.tgz`. Then, from a checkout of the same revision:

```bash
pnpm evidence:assemble --input <collected-dist> --output dist/release-evidence
pnpm evidence:verify dist/release-evidence --workspace .
```

Assembly refuses to run when any required file is missing, when an evidence record names
another source revision, when a platform record names the wrong platform, when an
installer lacks `LICENSE` or `THIRD_PARTY_NOTICES`, or when credential material is found.

Set `SOURCE_DATE_EPOCH` to a fixed Unix timestamp when byte-stable bundle metadata is
required:

```bash
SOURCE_DATE_EPOCH=1790000000 pnpm evidence:assemble --input <collected-dist>
SOURCE_DATE_EPOCH=1790000000 pnpm evidence:verify dist/release-evidence --workspace .
```

## Bundle Contents

```text
dist/release-evidence/
  bundle.json
  SHA256SUMS
  files/
    LICENSE
    THIRD_PARTY_NOTICES
    source-manifest.json
    smoke/{linux,darwin,windows}-tui.json
    e2e/personas-{linux,darwin,win32}-x64.json
    protocol-smoke/{openai-chat,openai-responses,anthropic-messages}.json
    benchmarks/ab.json
    installers/
      neonforge-{linux,darwin,windows}-x64.tgz
      release-{linux,darwin,windows}-x64.json
```

`bundle.json` records the schema, application version, source revision, Git commit,
generation time, platform/protocol coverage, legal files, checks, and every payload's
SHA-256 hash and byte size. `SHA256SUMS` covers `bundle.json` and every payload.

Verification performs no network request and reads no provider credential. It checks the
source revision against the supplied checkout, requires the current Git commit, checks
every hash and byte size, validates the evidence schemas and thresholds, extracts each
installer to confirm legal files and MIT metadata, and rejects credential-shaped fields.

## Failure Handling

- A missing or stale platform record blocks assembly; do not substitute another platform.
- A failed hash, checksum sidecar, schema, threshold, installer, or credential scan blocks
  verification.
- A failed native job produces no attestable bundle. Preserve its logs and fix the
  underlying failure rather than selecting a successful subset.
- Without a configured Git remote, the workflow and local verifier can be tested, but no
  GitHub attestation or release attachment exists until the repository is pushed and the
  workflow is run with authorization.
