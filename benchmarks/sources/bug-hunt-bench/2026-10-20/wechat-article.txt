先弄明白 harness 到底是个什么

大多数人的注意力都停在模型名字上，买算力、比参数、盯版本更新，却忽略了模型和你的活儿之间还隔着一层。你敲下那句需求之后，谁去读整个仓库、谁决定先看哪几个文件、长文件怎么切碎了喂进去、改错了是原地重来还是换个思路、工具总共能调用几次，这些活儿都不归模型管，是 harness 在管。打个比方，模型是发动机，harness 是把这台发动机装上车时配的那套底盘和传动。同一台发动机配不同的底盘，跑出来的成绩能差出去一大截。

这次被拿来当发动机的，是 DeepSeek V4.1 Flash 1017 这个版本。九套不同的 harness，装的全是它。

89 次复跑，为的是把运气挤掉

单次 benchmark 的分数，看个热闹还行，当真就悬了。采样时的随机性抖一下、某次工具调用卡了半秒、某个任务恰好撞进模型的舒服区，几分上下就跟着晃。一次样本的偶然成分太重，拿它下结论风险不小。

所以这次的安排是把整套 benchmark 翻来覆去跑了 89 次，摊在 9 个 harness 上，统一开 high effort 档，每个任务给 5 次尝试机会。重复跑的意义正在于把偶然撞上的好运和偶然踩到的坑平均掉，剩下的部分才接近这个 harness 本来的成色。老话讲「试玉要烧三日满，辨材须待七年期」，说的就是这回事，真假不是一次就能见分晓的。

成绩单：Pi 和 Grok Build CLI 打平

high effort 档，每个任务 5 次尝试，最后得分排下来是这样：

Pi harness 40.4

Grok Build CLI 40.4

DeekSeek 39.2

OpenCode 2.0 38.6

OpenCode 36.6

Claude Code 36.4

Codex 33.2

Hermes Agent 32

Kilo Code 31.8

排在头里的是 Pi harness 和 Grok Build CLI，两家都是 40.4，正好打平。第三名 DeekSeek 拿到 39.2（原文是这个拼法，照抄没改），跟头名差 1.2 分。末位的 Kilo Code 是 31.8。同一颗模型，头尾却拉出了近 9 分的距离，这层套装的影响之大，估计超出不少人的预期。

为什么换个 harness，同一个模型就换了个分数

这背后的细账这次没摊开讲，只能猜个大概，跑不出这四件事的范围。

一是喂进去的上下文不同。同一个仓库，有的 harness 舍得把相关部分整片塞进去，有的只给一小段。模型看到的东西不一样，判断就不一样。

二是给模型的活动余地不同。有的允许它先摸清全局再动手，反复读反复改；有的要求一次只动一处，工具调用次数也掐得死。5 次机会怎么用、能不能用满，调度权全在 harness 手上。

三是出错之后怎么收拾。报错了是原样重试、换个写法再试、还是当场认输，结果能差很远。

四是 token 花在什么地方。high effort 意味着舍得烧 token，但烧在检索上还是烧在反复自查上，效果是两码事。

这几条叠起来，大概率能解释头尾那段落差的绝大部分。换 harness 的收益或许比换模型还实在，至于实在多少，这次没给拆分数据。

Codex 超时这件事，比它的分数更值得看

Codex 拿到 33.2，排第七。但看这张表不能漏掉一条备注：它有好几次超过了每个仓库允许的 3 小时上限，任务没做完。没做完的部分，按它当时跑到的位置算了分。

这就有两层意思。一层是对 Codex 可能有点冤，时间给够的话它的分数估计不会停在这个位置。另一层又反过来，能不能在 3 小时内收工，本身就是干活能力的一部分，真实项目里没人因为你差一点就跑完而多批三个钟头。所以这个分数不能当成它的真实水平，也算不上不公平。

这张表能用在哪儿

这次测下来的结论是，Pi、Grok Build CLI、OpenCode 2.0 这三家，像是眼下最能打的通用 harness。「通用」这两个字的分量要掂清楚：它们摊在多种任务上平均分依旧站得住，没有靠某一类偏门的活把分数垫起来。古人说举一反三，通用能力的高低，估计主要就体现在这种迁移上。

但要把它推到自己手头的活儿上还早。这次跑的任务、语言、限制就那么些，换一套环境名次大概率要重排；Codex 的超时问题如果放宽时限，排序也会动。这张表更适合拿来筛几个候选，别当成终局的判决书。「兼听则明，偏信则暗」，多试几套 harness，用自己的仓库跑一遍，比盯着别人的排行榜管用。说到底纸上得来终觉浅，绝知此事要躬行，自己机器上那版分数才作数。
